## 前端连接失败根因（关键 Bug）
- **现象**：浏览器打开 http://localhost:5173 显示 WS 连接失败（红点），但 `verify_e2e.py` 17/17 全 PASS（假绿）。
- **根因**：`server/ws_server.cpp` 手写 SHA1 初始向量第 5 个字错写为 `0xE1032547`，正确应为 `0xC3D2E1F0`。导致 `sha1_base64()` 算出的 `Sec-WebSocket-Accept` 错误 → **浏览器严格校验 accept 失败、拒绝握手、onerror**；python ws 客户端不校验 accept 所以一直"假绿"。
- **修复**：SHA1 h[4] 改为 `0xC3D2E1F0`；并修 `send_text` 的 `(char)text.size()` 在 >125 字节时的符号溢出（统一用 broadcast 的 126/127 扩展长度编码）。
- **验证**：用标准库 `hashlib` 复算 accept 与服务器返回对比 → `MATCH: True`（等价于浏览器握手校验）；真实 Chromium 经 CDP 读 `.conn-dot` 类名 = `open`、`body` 含 "WS Connected" + 实时转速/角度 → 端到端确认连接成功。后端 E2E 重跑仍 17/17。
- **教训**：手写 RFC6455 WebSocket 服务器，**Sec-WebSocket-Accept 必须用标准库（hashlib/crypto）独立复算并比对**，不能只靠不校验 accept 的 python 客户端验证；否则浏览器侧会静默失败。
- **附带加固**：`Motor3D.tsx` 给 `new THREE.WebGLRenderer()` 加 try-catch（WebGL 不可用时渲染占位而非抛错）——否则无头/弱 WebGL 环境单组件崩溃会拖垮整个 React 树白屏。`tsc` strict 0 错误，`vite build` 通过。

## V1.2.1 需求落地（速度/电压/负载量程 + 三窗口示波器）

## V1.2.2 两个假数据 Bug 修复（speed loop）
- **Bug 1（电机停止后示波器显示目标转速而非 0）**：`cmd_stop()` 此前只置 `status=STOPPED`，`step_one` 停跑后 `rotor_angular_vel` 冻结在末值（一旦达目标即 = 目标值），示波器据此画出"目标转速"。修复：`cmd_stop` 置 `rotor_angular_vel=0` 并清空速度环积分上下文 `speed_pi_ctx_`。
- **Bug 2（KI=0 无变化）**：根因是 `pi_unwind()` 做 `I=(sat-bias)/i_gain`，**KI=0 时除以零 → Inf/NaN** 污染转矩与整个电机状态，故 KI=0 不像纯比例环工作（表现为"无变化"/NaN）。修复三处：
  1. `update_speed_loop` 饱和钳位处：仅当 `i_gain>0` 才调 `pi_unwind`，否则把 `integral=0`（纯 P 无积分项可反算）。
  2. 同函数 `pi_control` 之后：`if (i_gain==0) integral=0`，丢弃累积 windup 并防止长时累积溢出。
  3. `cmd_speed_pi`：`ki==0` 时立即清空 `speed_pi_ctx_.integral`（纯 P 干净复位，杜绝后续饱和除以零）。
  - 物理验证（E2E-22）：KI=0 + 负载 0.1Nm → 稳态转速 95.0 rad/s（比无载 99.9 低 **4.9 rad/s 稳态误差/droop**，符合纯 P `droop=负载/Kp`）；恢复 KI=0.5（E2E-23）→ 100.1 rad/s（积分消除静差）。此前 KI=0 因 NaN 完全失效。
- **用户追加**：stop/reset 时清除 KI 累积。`cmd_stop` 已清积分；`cmd_reset`→`reset_state` 本就 `speed_pi_ctx_=PiContext{}` 清积分；`cmd_speed_pi(ki=0)` 也清积分。

## V1.3 编译/访问修复 + 速度瞬态可视化 + 响应回归

### 1. 编译问题根因（重要，跨 Windows C++ 工程通用）
- **现象**：`server/build.bat` 用 `where g++` 选编译器 → 本机 PATH 第一个是 **PainterEngine 捆绑的精简 mingw-w64 8.1.0**（无 `timeapi.h`），报三个看似无关的错：
  `main.cpp: fatal error: timeapi.h: No such file or directory` /
  `high_res_sleep.h: 'CreateWaitableTimerExW' was not declared` /
  `ws_server.cpp: 'inet_pton' was not declared`。
- **单一根因**：该工具链声明的 Windows 版本过低。`_WIN32_WINNT < 0x0600` 时 Windows 头**故意隐藏**所有 Vista+ API；精简发行版只带 `mmsystem.h` 不带 `timeapi.h`。
- **修法**：新增 `server/win_compat.h` —— 把可移植性契约写进代码：`_WIN32_WINNT=0x0601` +
  `__has_include(<timeapi.h>)` 否则回退 `<mmsystem.h>`。**两套工具链实测均可零警告编译**
  （MSYS2 g++ 15.2.0 / 精简 mingw 8.1.0，exe 2,487,085 B 静态链接）。
- **`build.bat` 改造**：不再"看路径选"，改成**用真实 TU 做探针**——每个候选 g++ 先
  `-fsyntax-only main.cpp`，通过才采用；全不通过则打印最后一次探针日志 + 安装提示。
  支持 `build.bat nopause`（供 start.bat 调用，旧版 `pause` 会挂住）与 `MOTORFORGE_GXX` 覆盖。
- 注意 `winsock2.h` 必须在 `windows.h` 之前（否则 `#warning` 在 `-Werror` 下变硬错误）。
- **沙箱坑**：MSYS2 的 `g++.exe` 从 Bash 工具直接调用**静默失败**（exit 1 / 零输出；
  `cc1plus.exe` 直接跑 exit 127），但用 **Python `subprocess.run` 调同一个 exe 完全正常**。
  ⇒ 本机跑 MSYS2 工具链一律用 Python 驱动（`cmd /c build.bat` 也从 Python 起）。探针会自动判定并回退，
  所以在沙箱里 build.bat 会选中 PainterEngine 那套——这**正好验证了探针逻辑有效**。

### 2. 访问问题根因
- `web_ui/node_modules` 缺失时 `start.bat` 直接 `call npm run dev` → 必然失败。
- 前端 `App.tsx` 硬编码 `store.connect("127.0.0.1", 18098)`；Vite `server.host=true` 会在局域网可达，
  但从别的机器打开页面时 WS 指向**浏览器自己的 loopback** → 永远 Disconnected。
- **修法**：`start.bat` 增加 node/npm 定位（`npm.cmd` → 回退 `node <npm-cli.js>`）+ 依赖引导
  （缺 `node_modules/vite` 才 `npm install`）；新增 `web_ui/src/sim/net.ts` 以
  `window.location.hostname` 推导 WS 主机。`timeout /t 1` 换成 `ping -n 2`（stdin 被重定向时 timeout 会报错）。
- **实测**：`start.bat` → 5173 与 18098 双双就绪，vite 打印 Local + Network(192.168.3.5)。

### 3. "真实速度显示不符合预期"根因（不是 controller 的问题）
- SPEED 窗锁定量程 0–1100 rpm，而 0.1 N·m 阻力只造成 **1.09 rad/s ≈ 10.4 rpm** 跌落
  → 占画面高度 **约 1%（3–4 px）**，肉眼完全看不出"跌落后回归"。
- **修法（前端）**：SPEED 窗三档量程 `全局 / 自动 / 偏差 Δ(rpm)`；偏差模式以目标转速为零线、
  对称自适应缩放；窗下加瞬态数值读数（Δ当前 / Δ跌落 / @t / 调整时长 / 稳态Δ）。
  PID 面板加三档预设（纯P / 标准PI / 高增益PI）+「读取当前值」，默认值对齐后端真实值
  （旧默认 Kp=0.5/Ki=5/限幅 2 N·m 与后端 0.05/0.5/0.1616 不符，2 N·m 是执行器能力的 12 倍）。
- **顺带修掉两个真 bug**：
  ① `Scope` 的 `on` 映射只在首次渲染初始化 → 运行时切换通道时新通道为 `undefined`，
  `active` 为空 → **整窗不画线**（加 useEffect 同步）；
  ② 瞬态读数原对整段缓冲取 min → **启动加速斜坡被误报成"跌落"**（-948 rpm）；
  改为从"最近一次扰动起始点"统计，未达目标时显示「加速中」。

## 21:00–22:0x 追加 — "为什么空载时 PWM 值还在跳？"

用户提问：空载下 PWM 读数一直跳动。**结论：不是控制器问题，也不是噪声；是"旋转矢量 + 遥测欠采样"，
而且他当时的实例还叠加了"电压饱和"。**

### 判据（全部可复现）
1. **duty 是电角度的确定函数**：把 434 个稳态采样**按电角度分 36 箱**，箱内/总体离散度 = **6.0%/5.4%/5.5%**（A/B/C）
   → 塌缩 17 倍。原始 p-p 0.3065，角度分箱还原的 p-p 0.2898。
   **方法要点**：混叠打乱的是时间顺序，(θ_e, duty) 对仍是有效采样点，所以"分箱"能反混叠，不需要改采样率。
2. **相位**：拟合 `duty = a + b·cosθ + c·sinθ`，A→B **238°**、A→C **119°**（理论 240°/120°）；
   `θ_e == 4·θ_m` 偏差 0.0000°（快照自洽）。
3. **空载≠零电压**：`|V_qd|` 对转速严格线性，斜率 **0.04913 V/(rad/s)**，理论 `n_pp·bEmf0/kClarke = 4×0.01/0.8165 = 0.04899`（+0.29%）。
   空载 100 rad/s：`|V_qd| = 4.90 V` → `m = 0.408`。**这是反电动势，逆变器必须输出它才能维持 Iq=0。**
   斜率吻合说明 `kClarkeScale = √(2/3)` 的帧关系是 `scaled_v = physical_peak / kClarke`。
4. **摆幅解析式**：`duty p-p = √2 · m`（min-max SVPWM 几何，非拟合）→ 半摆幅 `m/(2√2)`。
   实测 0.1449 vs 预测 0.1443（**0.4%**）。数值扫描确认 `m ≤ √2` 线性，超过则钳位到 0/1。
5. **链路闭合**：用上游 `get_avg_voltage_ab` 从三路 duty 反算实际施加电压，与指令 `|V_qd|` 比：
   5 个工作点比值 **0.9977 / 1.0006 / 0.9999 / 1.0001 / 0.9997** → duty 忠实编码指令矢量。
6. **混叠比**：帧间隔**实测 42–45 ms 仿真时间**（20 ms 墙钟 × speed_scale=2 + 循环开销），
   100 rad/s 时 f_e=63.66 Hz → **2.7–2.8 电周期/帧**；25 rad/s 时 0.69（所以低速看着不跳）。

### 未归因项（如实记录）
`vq = backEMF + R·iq/kClarke` 这个手推模型：空载吻合 **-0.11%**，带 0.05 N·m 负载差 **-3.8%**（vd 差 13%）。
因为 P-05 已证明"施加电压 = 指令电压（0.11%）"，残差在**手推模型侧**，不是逆变器。
**故意没有把这条写进断言**，只在 `verify_pwm.py` 里打印说明。
