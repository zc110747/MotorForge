## 前端连接失败根因（关键 Bug）
- **现象**：浏览器打开 http://localhost:5173 显示 WS 连接失败（红点），但 `verify_e2e.py` 17/17 全 PASS（假绿）。
- **根因**：`server/ws_server.cpp` 手写 SHA1 初始向量第 5 个字错写为 `0xE1032547`，正确应为 `0xC3D2E1F0`。导致 `sha1_base64()` 算出的 `Sec-WebSocket-Accept` 错误 → **浏览器严格校验 accept 失败、拒绝握手、onerror**；python ws 客户端不校验 accept 所以一直"假绿"。
- **修复**：SHA1 h[4] 改为 `0xC3D2E1F0`；并修 `send_text` 的 `(char)text.size()` 在 >125 字节时的符号溢出（统一用 broadcast 的 126/127 扩展长度编码）。
- **验证**：用标准库 `hashlib` 复算 accept 与服务器返回对比 → `MATCH: True`（等价于浏览器握手校验）；真实 Chromium 经 CDP 读 `.conn-dot` 类名 = `open`、`body` 含 "WS Connected" + 实时转速/角度 → 端到端确认连接成功。后端 E2E 重跑仍 17/17。
- **教训**：手写 RFC6455 WebSocket 服务器，**Sec-WebSocket-Accept 必须用标准库（hashlib/crypto）独立复算并比对**，不能只靠不校验 accept 的 python 客户端验证；否则浏览器侧会静默失败。
- **附带加固**：`Motor3D.tsx` 给 `new THREE.WebGLRenderer()` 加 try-catch（WebGL 不可用时渲染占位而非抛错）——否则无头/弱 WebGL 环境单组件崩溃会拖垮整个 React 树白屏。`tsc` strict 0 错误，`vite build` 通过。

## V1.2.1 需求落地（速度/电压/负载量程 + 三窗口示波器）
- 最终需求（按顺序）：① 电压仅 12V/24V 两档；② 速度 1~100 rad/s；③ 负载量程 = 100 rad/s 处电机最大转矩（压力设置范围上限）。
- **后端物理修正（根因：之前 400rad/s+2Nm 量程使弱电机在 12/24V 下"加负载后转速变负/PI 极慢"）**：
  - `max_torque_at(omega)`：dq 电压限制转矩包络，解 `(a·iq)²+(b·iq+c)²=Vmax²`（`a=ωₑL,b=R,c=ωₑλ,Vmax=Vbus·kClarke`,`λ=kClarke·bEmf0·1.5`），返回 `λ·iq`。
  - `recompute_limits()`：`load_max_torque_ = max_torque_at(100)*0.95`，并令 `speed_torque_limit_=load_max_torque_`（速度环转矩限幅 = 执行器能力，杜绝命令不可达转矩）。
  - `cmd_motor_parameter` 母线电压：`value != 12 && != 24` → 拒绝；改电压后 `recompute_limits()`。
  - `cmd_load_configure`：`applied.torque>load_max_torque_` 时钳位（负载永不超过执行器能力 → 转子永不在阻力下反转）。
  - `step_one()`：`rotor_angular_vel<0` → 0 兜底（物理上负载只能减速/停转，不会反转）。
  - `rotor_inertia_` 0.01→0.005（速度环已饱和，spin-up 由转矩限制，此值唯一能压"PI 慢"的杠杆）：100 rad/s 约 3s 达稳（原 ~6s）。
  - **移除 update_speed_loop 的 TEMP DBG fprintf**（调试已确认：spin-up 正确饱和至 0.1616、稳定后回落 ~0；之前"卡在 0.055"是稳态平衡负载的正确 PI 行为，非 bug）。
- **验证（后端）**：临时探针对 18102/18103 实测 —— 无负载达 100 rad/s 无负速；中等负载 0.05→转速 ~99.6 且 Tcmd≈0.05；满负载 0.162→转速 ~92 仍 ≥0；过载 10Nm→钳到 0.1616、转速 ~87 不反转；撤载回到 100。全部 ✅。
- **前端**：
  - `store.ts`：`params` 增 `loadMaxTorque`，`zeroState` 同步（rotorInertia 0.005）。
  - `ControlPanel.tsx`：`MAX_TARGET_RAD=100`、`min=1`；新增 **12V/24V 分段按钮**（发 `motor.parameter bus_voltage`），并显示当前 `loadMaxTorque` 作为负载上限提示。
  - `LoadPanel.tsx`：转矩滑块 `max` 改为动态 `store.latest.params.loadMaxTorque`（12V≈0.055 / 24V≈0.16），step 0.005，显示量程。
  - `Oscilloscope.tsx`：**四窗 → 三窗**，删除右下"Speed·稳定后放大"，左列 SPEED·全局（锁定量程，占两行高）｜右列上 PWM + 下 SIGNALS。固定量程改 `[0,1100]` rpm（覆盖 0–100 rad/s≈955rpm）。
  - `index.css`：新增 `.scope-3col/.scope-stack/.scope-tall`（左列 flex 拉伸、canvas `flex:1 1 auto` 占双行）与 `.seg/.seg-btn`（电压分段）。

## V1.2.2 两个假数据 Bug 修复（speed loop）
- **Bug 1（电机停止后示波器显示目标转速而非 0）**：`cmd_stop()` 此前只置 `status=STOPPED`，`step_one` 停跑后 `rotor_angular_vel` 冻结在末值（一旦达目标即 = 目标值），示波器据此画出"目标转速"。修复：`cmd_stop` 置 `rotor_angular_vel=0` 并清空速度环积分上下文 `speed_pi_ctx_`。
- **Bug 2（KI=0 无变化）**：根因是 `pi_unwind()` 做 `I=(sat-bias)/i_gain`，**KI=0 时除以零 → Inf/NaN** 污染转矩与整个电机状态，故 KI=0 不像纯比例环工作（表现为"无变化"/NaN）。修复三处：
  1. `update_speed_loop` 饱和钳位处：仅当 `i_gain>0` 才调 `pi_unwind`，否则把 `integral=0`（纯 P 无积分项可反算）。
  2. 同函数 `pi_control` 之后：`if (i_gain==0) integral=0`，丢弃累积 windup 并防止长时累积溢出。
  3. `cmd_speed_pi`：`ki==0` 时立即清空 `speed_pi_ctx_.integral`（纯 P 干净复位，杜绝后续饱和除以零）。
  - 物理验证（E2E-22）：KI=0 + 负载 0.1Nm → 稳态转速 95.0 rad/s（比无载 99.9 低 **4.9 rad/s 稳态误差/droop**，符合纯 P `droop=负载/Kp`）；恢复 KI=0.5（E2E-23）→ 100.1 rad/s（积分消除静差）。此前 KI=0 因 NaN 完全失效。
- **用户追加**：stop/reset 时清除 KI 累积。`cmd_stop` 已清积分；`cmd_reset`→`reset_state` 本就 `speed_pi_ctx_=PiContext{}` 清积分；`cmd_speed_pi(ki=0)` 也清积分。
- **E2E 新增**：E2E-21（KI=0 无载达目标且有限）、E2E-22（KI=0+负载产生 droop 且 < 目标）、E2E-23（KI>0 同负载恢复目标）、E2E-24（stop→实际转速 0 非冻结目标）。重跑 **27/27 PASS**（port 18104，exit 0）。
- **交付**：`server/simulation_controller.cpp` 三处修复；`tools/verify_e2e.py` 4 个用例。prod `motorforge_server.exe` 已重链（16:46，同对象集）；用户 18098 实例需重启 start.bat 生效。前端无需改动（两 Bug 均为后端行为）。
